## From the alert to the trace and its logs

- **poison.** LogQL `{service_name="tenantflow-worker"} |~ "(?i)dead-letter"` returned "Dead-lettered invalid message
  drill-poison from notifications.order-events: Missing or malformed message id." with `MessageId`, `Queue` and
  `trace_id`; Tempo opened that trace: one consumer span `notifications.order-events process` with
  `tenantflow.messaging.outcome=dead_lettered`. The dead-letter queue panel showed `notifications.order-events.dlq = 1`.
- **probe.** The denial counter showed `tenant/not_a_member = 123` in 10 minutes; LogQL
  `{service_name="tenantflow-api"} |= "Access denied" |= "not_a_member"` returned the denials with `trace_id`; the trace
  showed `GET /v1/tenants/{tenantId}/products/` answered 404. No log, span or series named the caller or tenant (by
  design); the runbook now says so and points to the identity provider's events.
- **database.** LogQL `|= "Npgsql"` returned the connection failures ("Failed to connect to 127.0.0.1:55432") and the
  error query returned "Outbox poll failed"; TraceQL `{ span.db.system = "postgresql" && status = error }` returned the
  failing commands' traces. Symptom alerts did not reach firing during the 2-minute outage.
- **broker.** The `rabbitmq` health gauge read 0 for the Worker; the error logs returned "Health check rabbitmq with
  status Unhealthy ... 'RabbitMQ connection is closed'".
- **provider.** *Unresolved after a reconciliation check* showed `payment=3`, oldest 318 s, two minutes before the
  alert; *Provider calls by outcome* showed `simulator/create/unavailable` (the timeout) and `simulator/status/answered`
  (reconciliation asking, the answer still pending); LogQL `|~ "(?i)payment"` and TraceQL on `payments` statements
  returned the reconciliation runs. The expected time is 2 minutes to the first check, 5 minutes of age, 2 minutes of
  `for` and Alertmanager's group wait.
- **worker.** The heartbeat rate fell to 0 and `WorkerTelemetryMissing` (a cause) fired; the stale-outbox symptom it
  would otherwise produce needs 10 minutes and did not fire. A first attempt was aborted because the Worker was stopped
  before the drill's host check; it was restarted and the drill rerun.

## Fixed during the drills

- Runbook queries: case-insensitive dead-letter log filter; dead letters per consumer read from the counter itself
  (`increase()` misses a new counter's first sample); TraceQL for dead-lettered spans; the cross-tenant runbook no longer
  claims the trace names the caller; payment log and trace queries.
- `dev.ps1 drill`: Compose's stderr progress stopped the script between stopping and starting a dependency when the
  output was redirected (Windows PowerShell 5.1); the drill now tolerates it. The first `database` and `broker`
  attempts were cut off by this; their dependencies were restarted and the drills rerun.

## Observations for follow-up

- Quartz writes a connection failure's full exception text into the log message itself, which ADR-0031's processor
  cannot redact (it redacts exception objects). The text names the host and port only.
- In Development, ASP.NET Core's request-finished log (Information) carries the query string to Loki. Production logs
  `Microsoft.AspNetCore` at Warning, so it does not appear there; DP-A25 covers spans only.
