# SPEC-0008: Async files and reporting

- Status: Implemented (2026-10-22; approved 2026-10-21 by the user)
- Milestone: M8
- Owner: TenantFlow tech lead (user)
- Related: blueprint sections 6 (ImportsExports), 9 (upload and export limits, CSV injection), 10 ("Search, files, and
  exports"), 11 (background work), 13, 14 (slow report/export), 16 (import/export signals); ADR-0002, ADR-0011, ADR-0012,
  ADR-0023; ADR-0024 (Accepted); SPEC-0003; Open Decision 19

## Outcome
A catalog manager finds products by words in their name or SKU, loads thousands of products from a CSV file, and
downloads the catalog as a CSV file. Large files never hold a request open: an import or export is a job the client
polls. Jobs run in the Worker, one tenant's data each, within fixed limits; a crash resumes an import where it stopped
and never creates a product twice; a downloaded file cannot run a formula in a spreadsheet. Operators see how many jobs
wait and for how long.

## Acceptance criteria
**Search (Catalog)**
1. Given products of tenant A, when a `catalog.read` holder calls `GET .../products?q=blue mug`, then only products
   whose name or SKU contain every word (PostgreSQL full-text search, `simple` configuration, prefix match on the last
   word) are returned, with the existing visibility (inactive hidden from non-managers), order and cursor paging. Another
   tenant's matching products never appear. A `q` over 100 characters is 400.

**Storage (new ImportsExports module)**
2. Given the `IObjectStorage` port and its filesystem adapter, when a file is stored, then its key is generated by the
   server (`tenants/{tenantId}/{kind}/{fileId}`, never from a client file name), its size and SHA-256 are recorded in a
   tenant-owned `stored_files` row, and reading it back verifies the checksum. A key that leaves the storage root or
   names another tenant is refused.

**Imports (API and Worker)**
3. Given a `catalog.manage` holder, when they `POST .../imports/products` a CSV file (multipart, at most 5 MB) with an
   `Idempotency-Key`, then 202 with a job in `queued` and a `Location` to poll; the job row, its file row and its due row
   are committed before any row is processed (the upload is written between an intent commit and the queued commit).
   The same key and file again answer the same job; another file with that key is 422. A third active import of the
   tenant is 409 `imports_exports.too_many_jobs`. A customer gets 403; a file over 5 MB is 413; a non-CSV is 400.
4. Given a queued import, when the Worker runs it, then it reads the file in batches of 500 rows, creates or updates
   products by SKU through `Catalog.Contracts`, records each invalid row (row number, column, code; never the cell
   value) and moves to `succeeded` with created, updated and failed counts. A missing or unknown header column fails the
   job (`invalid_header`); more than 10,000 rows fails it (`too_many_rows`) before anything is written.
5. Given the Worker stopped after some batches (a crash, a lost lease), when the job runs again, then it resumes after
   the last committed checkpoint, no product is created twice and the counts are exact.
6. Given an import, when its owner tenant's manager reads `GET .../imports/{id}` and `.../imports/{id}/errors`, then 200
   with status, counts and the row errors (first 1,000). Anyone outside the tenant gets 404.

**Exports (API and Worker)**
7. Given a `catalog.manage` holder, when they `POST .../exports/products` with an `Idempotency-Key`, then 202 with a
   queued job; the Worker writes every product of the tenant (at most 100,000) page by page to a CSV file in storage and
   the job is `succeeded` with the row count and an expiry 7 days later. `GET .../exports/{id}/file` streams it to a
   `catalog.manage` holder of the tenant (404 to anyone else, 404 once expired). A crash restarts the export from the
   start and overwrites the same file.
8. Given a product name or SKU starting with `=`, `+`, `-`, `@`, a tab or a carriage return, when it is exported, then
   the cell is written with a leading `'` (OWASP CSV injection guidance) and every cell is quoted, so no spreadsheet
   evaluates it; an import of that file restores the original value.
9. Given a user of tenant A, when they read, download or poll tenant B's import or export, then 404 and nothing is read.

**Expiry and observability (Worker, Quartz)**
10. Given a succeeded export or a finished import, when its file expires (exports 7 days, uploads 7 days after the
    import finished), then a due row deletes the file and marks its row deleted; an upload stuck in `receiving` for an
    hour is failed (`upload_abandoned`) and its file deleted.
11. Given Quartz runs the `imports_exports.metrics` cron job every 30 seconds in the Worker, then gauges report queued
    jobs and the age of the oldest due job per kind (from the due rows, which hold ids only), and counters report job
    outcomes, failed rows and job duration. No tenant data is read by the cron job.
12. Then ImportsExports is a module with its own schema, Worker due-row registration and entries in the module,
    schema, role, RLS (forced 15 -> 20: stored_files, import_jobs, import_row_errors, catalog.import_batches, export_jobs), isolation matrix
    (25 -> 31 routes) and Migrator tests.

## Invariants
- A job acts on its own tenant only; storage keys are server-generated and tenant-prefixed.
- No file read or write and no Catalog call inside an ImportsExports transaction (CLAUDE.md rule 3).
- An import never creates two products for one SKU, however often a batch runs; a checkpoint only moves forward.
- An exported cell never starts with a formula character unescaped.

## Contract
Routes are under `/v1/tenants/{tenantId}`; all require `catalog.manage` except search (`catalog.read`).
| Operation | Answer |
|---|---|
| `GET /products?q=` | existing product page |
| `POST /imports/products` (multipart `file`, `Idempotency-Key`) | 202 `ImportJob` |
| `GET /imports/{id}`, `GET /imports/{id}/errors` | `ImportJob`, `{items: [{row, column, code}]}` |
| `POST /exports/products` (`Idempotency-Key`) | 202 `ExportJob` |
| `GET /exports/{id}`, `GET /exports/{id}/file` | `ExportJob`, `text/csv` stream |

`ImportJob`: id, status (`receiving`, `queued`, `running`, `succeeded`, `failed`), failure code, created/updated/failed
counts, timestamps. `ExportJob`: id, status, row count, expires at. CSV columns: `sku,name,price_amount,price_currency,
status`; decimal with `.`; UTF-8 without BOM. `Catalog.Contracts` gains `ICatalogImport` (upsert a batch by SKU) and
`ICatalogExport` (a page of products after a cursor).

## Data
`imports_exports.stored_files` (tenant_id, id, kind, key, content_type, size, sha256, created_at, expires_at,
deleted_at); `import_jobs` (tenant_id, id, status, file_id, idempotency_key, request_hash, checkpoint_row, counts,
failure_code, requested_by, timestamps; unique (tenant_id, idempotency_key)); `import_row_errors` (tenant_id, job_id,
row, column, code; key (job_id, row, column)); `export_jobs` (tenant_id, id, status, file_id, idempotency_key,
request_hash, row_count, failure_code, requested_by, timestamps); `workflow_timers`. Catalog: a stored generated
`search_vector tsvector` column (name and SKU with punctuation made spaces, so `PLATE-1` is the words `plate` and `1`)
with a GIN index; `import_batches` (tenant_id, job_id, batch_number, result jsonb, applied_at; key (tenant_id, job_id,
batch_number)), written in the batch's own transaction so a re-run batch replays its result instead of re-applying it.
All additive.

## Failure modes
- Crash between storing the upload and queueing: the job stays `receiving`; a retry with the same key and file writes
  the upload again and queues it, otherwise its abandon due row fails it in an hour (only a job still `receiving`).
- Crash mid-import: resume from the checkpoint; the batch since it is re-applied (upsert by SKU is idempotent).
- Storage unavailable: the job's due row backs off and retries (dead after 20 failures, ADR-0023); a failure on the last
  attempt ends the job as `run_failed`, and an active job not updated for 6 hours no longer counts toward the limit.
- A file that cannot be imported ends the job at once: not UTF-8, unclosed quote, a field over 1,000 characters or a row
  over 32 fields (`file_unreadable`), gone (`file_missing`) or altered (`file_corrupt`). Blank lines are skipped. An
  export over the file bound ends as `file_too_large`.
- A tenant submits many jobs: at most 2 active per kind; due rows of all tenants interleave by due time.

## Review fixes (2026-10-22, chosen by the user)
The M8 review found the upload route kept the API's 64 KiB body limit; it now allows the 5 MB file plus 64 KiB of
multipart framing (at most 4 form parts) and checks the `Idempotency-Key` first. Prices above the column's range
(999999999999999.9999) are a `price_amount` row error. Formula neutralizing also covers the full-width `＝ ＋ － ＠`.
A one-character last search word is matched whole, not as a prefix. Due-job gauges report a snapshot for 2 minutes
only, so a second Worker instance never reports a stale one. A due row is never re-armed by another tenant's schedule.

## Out of scope
Excel files, order and report exports, ranking search results, S3/GCS adapters and signed URLs (M12), malware
scanning, cancelling a job, import of stock or prices in other currencies than given.

## Decisions (approved by the user, 2026-10-21)
1. Storage (Open Decision 19): an `IObjectStorage` port with a filesystem adapter at `Storage:Root`, shared by the API
   and the Worker; downloads stream through the API (ADR-0024).
2. Imports and exports require `catalog.manage` (exports include inactive products).
3. Search uses the `simple` text configuration.
4. Row errors keep the row, column and code, never the cell value.
