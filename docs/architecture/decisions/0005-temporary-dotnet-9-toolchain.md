# ADR-0005: Temporary .NET 9 toolchain until the .NET 10 SDK is installed

- Status: Superseded by [ADR-0003](0003-dotnet-lts-and-dependency-policy.md) on 2026-10-24, when SPEC-0015 moved
  the repository to the .NET 10 SDK. Kept for the record of the interim period
- Date: 2026-10-19
- Owners: TenantFlow tech lead
- Related decisions: ADR-0003 (target remains .NET 10 LTS), ADR-0004

## Context
ADR-0003 selects .NET 10 LTS. The development workstation currently has only the .NET 9 SDK
(9.0.204, runtime 9.0.5), and installing .NET 10 is planned but scheduled for later. Work should
not stall in the meantime, and the gate must run against real tooling, not a simulated copy.

Known risks of the interim toolchain:
- .NET 9 is STS and reaches **end of support on 2026-11-10**.
- SDK 9.0.204 / runtime 9.0.5 is many servicing releases behind the latest 9.0 patch
  (9.0.319 / 9.0.21 on 2026-10-13), so it lacks published security fixes. This is acceptable for
  local development with no production traffic. It is not acceptable for anything deployed.

## Decision
Until the .NET 10 SDK is installed, the repository builds on .NET 9:

| Setting | Interim value | Target value (ADR-0003) |
|---------|---------------|-------------------------|
| `global.json` | `9.0.204`, `rollForward: latestFeature` | `10.0.402`, `rollForward: latestPatch` |
| `TargetFramework` | `net9.0` | `net10.0` |
| `AnalysisLevel` | `9.0-recommended` | `10.0-recommended` |
| `Microsoft.AspNetCore.Mvc.Testing` | `9.0.5` (matches installed runtime) | 10.0 runtime patch |
| `Microsoft.NET.Test.Sdk` | `17.14.1` | `18.x` |
| `public partial class Program;` | Declared in `Program.cs` | Removed (generated by .NET 10) |

`rollForward: latestFeature` lets any newer 9.0 SDK satisfy the pin, so patching the interim SDK
needs no repository change. Test SDK 17.14.1 is used because the 18.x coverage collector requires
the .NET 10 runtime and fails to load on a .NET 9 test host.

Everything else in ADR-0003 and ADR-0004 stays in force: central packages, lock files, locked
restore, NuGet audit, source mapping, cooldown, analyzers, and warnings as errors.

Out of scope: any .NET 9-specific code or package that would make the move to .NET 10 harder.

## Options considered
- **Wait for .NET 10 before continuing.** Keeps the target exact, but blocks progress.
- **Keep `net10.0` and verify on a patched scratch copy.** Used for the first M0 check. It cannot
  produce valid lock files or run the real CI configuration. Rejected as an ongoing approach.
- **Build on .NET 9 temporarily (chosen).** Real, reproducible gate today, at the cost of one
  scheduled migration.

## Consequences
- Lock files generated now target `net9.0` and are regenerated during the migration.
- CI installs the .NET 9 SDK from `global.json` until the migration.
- Every milestone done before the migration adds a little migration surface. Keep it small by
  avoiding APIs and packages that exist only for .NET 9.

## Migration checklist (to .NET 10)
> Carried out by [SPEC-0015](../../specs/0015-dotnet-10-toolchain-migration.md) on 2026-10-24. Two steps had gone stale:
> step 3 regenerates `packages.lock.json` files the user removed on 2026-10-23, and step 4 runs `scripts/verify.ps1`,
> which no longer exists (ADR-0037). The gate in `AGENTS.md` replaced it.

1. Install the .NET 10 SDK 10.0.402 or a later 10.0.4xx patch.
2. Restore the target values in the table above (`global.json`, `Directory.Build.props`,
   `Directory.Packages.props`) and delete the `Program` declaration in `Program.cs`.
3. Delete all `packages.lock.json` files, run `dotnet restore TenantFlow.sln`, and check that each
   test project's lock file lists `xunit.v3` and `Microsoft.NET.Test.Sdk`.
4. Run `scripts/verify.ps1` and the CI coverage command, then commit.
5. Set this ADR to `Superseded` and add the migration date to ADR-0003's status line.

## Validation
`scripts/verify.ps1` passes on the real repository with the interim toolchain, and the CI
coverage command produces a Cobertura file.

## Revisit triggers
The .NET 10 SDK is installed, or 2026-11-10 arrives, whichever comes first. M12 (cloud
deployment) must not start while this ADR is active.
