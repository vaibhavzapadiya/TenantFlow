# ADR-0024: Object storage port with a filesystem adapter, and asynchronous import and export jobs

- Status: Accepted (2026-10-21 by the user; every SPEC-0008 open question accepted with the recommendation).
  Amendment 1 (S3 adapter and deployed configuration): Accepted (2026-10-23 by the user).
- Date: 2026-10-21
- Owners: TenantFlow tech lead (storage, scope, job model chosen by the user on 2026-10-21; options recommended by Claude)
- Related decisions: [ADR-0002](0002-modular-monolith.md), [ADR-0011](0011-postgresql-row-level-security.md),
  [ADR-0012](0012-module-data-ownership.md), [ADR-0023](0023-subscriptions-renewal-scheduler-and-refunds.md);
  [SPEC-0008](../../specs/0008-async-files-and-reporting.md); blueprint sections 9, 10, 13, 14, 16
- Closes: Open Decision 19 (object storage emulator for local development)

## Context
M8 stores uploaded import files and generated exports, and runs long imports and exports without holding requests open.
The blueprint keeps files out of PostgreSQL, wants tenant-owned file metadata, asynchronous resumable jobs, and CSV
output safe against formula injection. Open Decision 19 asks which emulator stands in for object storage locally. The
cloud provider (Open Decisions 1 and 2) is decided only in M12.

## Decision
1. **Storage (Open Decision 19): a port, and a filesystem adapter now.** `IObjectStorage` (put a stream, open for read,
   delete) with a local-filesystem adapter rooted at `Storage:Root`, shared by the API and the Worker. Keys are
   generated by the server, `tenants/{tenantId}/{kind}/{fileId}`, validated to stay under the root. File metadata
   (tenant, kind, size, SHA-256, expiry) lives in a tenant-owned `stored_files` row under RLS. Downloads stream through
   an authorized API endpoint; no signed URLs. No emulator container: the S3 or GCS adapter is written in M12 with the
   cloud decision, against the same port.
2. **ImportsExports module** (schema `imports_exports`) owns jobs, row errors and file metadata, and reaches Catalog only
   through `Catalog.Contracts` (`ICatalogImport` upserts a batch by SKU; `ICatalogExport` reads a page after a cursor).
3. **Jobs are tenant-owned rows with a state table** (`receiving`, `queued`, `running`, `succeeded`, `failed`), run by
   the Worker from the module's due rows (`workflow_timers`, ADR-0023). Submission: an intent commit (job `receiving`
   and its file row), the file write, then a commit to `queued` with the due row. Imports work in batches of 500 rows
   and checkpoint after each; a batch is idempotent (upsert by SKU), so resuming after a crash re-applies at most one
   batch. Exports restart from the beginning on a crash and overwrite the same file. Submission takes an
   `Idempotency-Key` stored on the job (with a request hash); at most 2 active jobs per tenant and kind.
4. **Limits:** uploads 5 MB and 10,000 rows; exports 100,000 rows; files expire after 7 days (deleted by due rows);
   row errors keep a code and column, never the value.
5. **CSV safety:** every cell quoted; a cell starting with `=`, `+`, `-`, `@`, tab or carriage return gets a leading
   `'` on export, removed again on import of such a cell.
6. **Search:** a stored generated `tsvector` (`simple` configuration) over name and SKU with a GIN index; `q` filters
   the existing keyset-paged list, order unchanged.
7. **Observability:** a Quartz cron job (`imports_exports.metrics`, every 30 seconds) reads the module's due rows (ids
   only) for queue depth and oldest age per kind; job outcomes, failed rows and durations are counters and a histogram.

## Amendment 1: S3 adapter and its deployed configuration

- Status: Accepted (2026-10-23, approved by the user with every recommendation in SPEC-0012 questions 15 to 20;
  SPEC-0012 S3c, amendment 1).
- Change:
  - A second adapter of the same port on Amazon S3 (AWSSDK.S3, the only new package; approved with SPEC-0012). Local
    development keeps the filesystem adapter; S3 is exercised against a pinned Adobe S3Mock image in the database test
    run only, never in the Compose stack (user, 2026-10-22).
  - The adapter is chosen by `Storage:Provider` (`filesystem` or `s3`), validated at startup with the keys each one
    needs (`Storage:Root`; `Storage:S3:Bucket` and `Storage:S3:Region`). The filesystem must be switched on with
    `Storage:Filesystem:Enabled`, as the payment simulator is; only local Development settings and test hosts do so
    (user, 2026-10-23, at implementation: test hosts run in Production with filesystem storage).
  - Credentials come from the task role through the SDK's default chain; no access key exists in configuration.
  - A put streams into `/tmp` while counting bytes and computing the SHA-256, then stores the object with one
    `PutObject` carrying that checksum, so S3 verifies it and no partial object is ever visible under the key. The
    temporary-file sweep has nothing to do on S3; the bucket's lifecycle rule aborts incomplete multipart uploads.
  - Keys, the `stored_files` metadata, the checksum check on read and the authorized download endpoint are unchanged.
    Still no signed URLs. When storage fails during a download, the endpoint answers 503 Problem Details with no
    provider detail; a missing object stays 404. Readiness does not call the bucket.
- Options considered: the provider inferred from whether a bucket is set (rejected: a missing setting would fall back
  to the filesystem silently); multipart upload straight from the request stream (more code, and the size and hash are
  known only at the end); a readiness check against the bucket (rejected: a cost per probe, and an S3 blip would take
  the API out of the load balancer).
- Consequences: deployed environments need no shared volume; the API and Worker need `/tmp` space for one object per
  concurrent put (at most 5 MB for an upload, an export's size for an export); integrity rests on both S3's checksum
  and the existing check on read.

## Options considered
- Storage: filesystem adapter behind a port (chosen by the user: no container, no dependency; no S3 semantics such as
  signed URLs or multipart until M12) vs an S3 adapter tested against SeaweedFS (Apache-2.0; a new stateful container
  and AWSSDK.S3) vs Adobe S3Mock (test-only) vs MinIO (AGPL; its community edition stopped publishing images in 2025)
  vs LocalStack (its free tier now needs an account token).
- Jobs: due rows and Quartz (chosen, transactional with the job's state, no new infrastructure) vs a RabbitMQ job queue
  (a queue and consumer more; resumability still needs database checkpoints).
- Module: a new ImportsExports module (chosen, the blueprint's owner; an orders export later reuses it) vs inside Catalog.
- Search: PostgreSQL full-text search (the blueprint's starting point) vs a search engine (no measured need).

## Consequences
- Easier: no new container; the storage port isolates the cloud choice; jobs reuse the M7 scheduler and its
  dead-lettering.
- Harder: the API and Worker must share a file root (a volume in deployment until M12); downloads use API bandwidth;
  four more forced-RLS tables and a new module.
- Follow-up: S3/GCS adapter and signed URLs (M12); malware scanning (M9); Excel; job cancellation; per-tenant fairness
  beyond the active-job cap (M11).

## Validation
SPEC-0008 criteria with tests; break-it proofs for cross-tenant job and file access, storage key validation,
idempotent submission, resume without duplicates, the active-job cap and formula neutralizing.

## Revisit triggers
The cloud decision (M12); files too large to stream through the API; a need for signed URLs or uploads straight to
storage; search relevance needs beyond full-text filtering.
